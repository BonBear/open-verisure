Not seen again in the following runs (including a 7 h armed run on 2026-11-17/18 with 922 polls, none more than 45 s apart), and the Otii showed no supply cut-off then. - [ ] **Counter seed from the device's own log (review 2026-11-17, low).** The flash scripts seed the counter with the gateway's last block + 2, but a device can have used more blocks than the gateway saw (boots, lost packets). Reading the old log (0x7800-0x7FFF) over the debug interface before the chip erase and seeding with max(gateway, device) + 1 would close that. Needs a flash-read in the ESP_CC_Flasher API.
- [ ] **Rate limit for a rattling reed (review 2026-11-17, low).** A door at the magnet threshold sends a packet per change (up to ~10 per second); a backoff like the camera's tamper backoff would cap it.
- [ ] **Gateway USB serial output stalled once (low).** On 2026-11-18 a script kept COM9 open without reading for ~1.5 h while it retried opening it; after it was killed the gateway sent no more text on USB (radio and MQTT kept working) until `reboot` on the console. Not reproduced: holding the port unread for 3 and 25 min and then killing the process left the console working (2026-11-18, firmware 5319b54). Note: the Arduino core's `USBCDC::write` loops without a timeout while the host has the port open but does not read. If it comes back: note what held the port; scripts must close the port when they stop reading.

- [ ] **ESP_CC_Flasher changes are only on the bench PC.** The serial command firmware (`src/serial_cmd.cpp`/`.h`) and edits to 10 files (ESP32-C3 pins, web, library fixes) are uncommitted in the local ESP_CC_Flasher checkout (upstream atc1441/ESP_CC_Flasher, GPL-3.0, at c61a418). Everyone else needs them for `--serial`, and a disk failure would lose them: publish a fork (or a patch with its GPL notice) and link it from the setup guide and `documentation/hardware_cc_flasher.md`.
- [ ] **Door sensor idle current: the 0.5 s tick starts the crystal (2026-11-19).** Idle is 26.3 µA at 3.0 V (Otii, 2.6 h, lid on), and ~24 µA of it is the tick: every wake-up starts the 27 MHz crystal, ~4 ms at 5.4 mA (12 µC), although a tick that sends nothing needs no crystal. Handling the tick on the HS RCOSC and starting the crystal only before a packet would bring idle to a few µA. The radio was once silent when the crystal was started only for the transmission (2026-11-16), so this needs a bench test of every event and the heartbeat. Branch `door-rcosc-tick` (built, reviewed, not flashed) does it; with it the 36 kHz sleep clock is recalibrated only while the crystal runs, i.e. per packet, so also check the heartbeat interval over a few hours (drift with temperature). The camera's tick does the same.
- [ ] **Shared CC1110 code (external review 2026-11-18).** About 400 lines are copied between the door sensor and camera `main.c` (clocks, sleep timer, AES, battery ADC, radio and DMA, the counter log), so a fix in one misses the other (the AES wait was one). Move them into a shared source both builds compile; rebuild and bench-test both devices after it.
- [ ] **CI (external review 2026-11-18).** A GitHub Actions workflow that builds the gateway (`secrets.h.example` as `secrets.h`), both CC1110 firmwares with SDCC (`config.h.example` as `config.h`, `--compile-only`) and runs `derive_key.py` against a known AES test vector.
