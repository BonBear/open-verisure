- [ ] **Counter seed from the device's own log (review 2026-11-17, low).** The flash scripts seed the counter with the gateway's last block + 2, but a device can have used more blocks than the gateway saw (boots, lost packets). Reading the old log (0x7800-0x7FFF) over the debug interface before the chip erase and seeding with max(gateway, device) + 1 would close that. Needs a flash-read in the ESP_CC_Flasher API.
- [ ] **Rate limit for a rattling reed (review 2026-11-17, low).** A door at the magnet threshold sends a packet per change (up to ~10 per second); a backoff like the camera's tamper backoff would cap it.
- [ ] **Gateway USB serial output stalled once (low).** On 2026-11-18 a script kept COM9 open without reading for ~1.5 h while it retried opening it; after it was killed the gateway sent no more text on USB (radio and MQTT kept working) until `reboot` on the console. Not reproduced: holding the port unread for 3 and 25 min and then killing the process left the console working (2026-11-18, firmware 5319b54). Note: the Arduino core's `USBCDC::write` loops without a timeout while the host has the port open but does not read. If it comes back: note what held the port; scripts must close the port when they stop reading.

- [ ] **Shared CC1110 code (external review 2026-11-18).** Done on 2026-11-19 for the code that was identical: `cc1110_common/` (AES, clock switching, sleep timer, counter log) is included by both `main.c` files where the code was, and both binaries are byte-identical to before (SDCC 4.6 and 4.5), so no bench test is needed for it. Left, because the copies differ: `delay_ms` (loop count 2100 vs 2180), the battery ADC (the camera throws the first conversion away), `ctr_boot`, `radio_init` and `radio_send_dma`; sharing them changes a binary and needs a bench test of the device.
- [ ] **More than one camera (low).** The gateway keeps one picture buffer and one delta base (`image_receiver.cpp`) and the web page shows the first camera; a second camera's deltas would splice into the other's picture. Make both per camera if a second camera is added.
- [ ] **Command queued during delivery is taken cold (bench 2026-11-20).** With the ACK rule (a command goes out first only on an ACK-free poll), a command queued while the previous one is being delivered (e2e chain: D3 queued right after D1's delivery) is held back at the poll after the picture, because that poll carries D1's ACK. The camera closes `pic_open` and powers the Blackfin off after `BF_KEEP_ON_S`, and polls again only after `BF_POLL_S` / `BF_POLL_DISARMED_S`, so D3 is taken cold and becomes a full picture: "a delta among the D3s" fails on a clean link (full, full). Possible fix: the camera polls again after `BF_ACK_POLL_TICKS` when it has just reported an ACK and the Blackfin is on (or relax the e2e check).
