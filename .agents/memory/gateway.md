# Memory: Gateway (ESP32-S2, 868Receiver)

## 🌐 Gateway (ESP32-S2, 868Receiver)
- [2026-10-22] [ESP32-S2/Coexistence]: Use only ADC1-domain pins for the SPI bus to the CC1101; ADC2 pins create switching noise that knocks out the ESP32-S2's 2.4 GHz Wi-Fi receiver.
- [2026-10-22] [PlatformIO]: The gateway is compiled with PlatformIO; do not disturb the captive portal and MQTT tasks in FreeRTOS.
- [2026-11-18] [GATEWAY/CORE3_SPI]: On Arduino core 3.x (espressif32 8.x) pinMode() on a pin that SPI uses detaches it from the SPI peripheral, and a second SPI.begin() does nothing. SmartRC-CC1101 3.x calls pinMode() in setSpiPin(), so the CC1101 read 0x00 until SPI was re-attached after it (radioSpiAttach: SPI.end + SPI.begin). Pin lib_deps (SmartRC-CC1101 jumped from 2.5.7 to the 3.x rewrite).
- [2026-11-18] [GATEWAY/USB_CDC_STALL]: If a host holds the USB serial port open without reading, the gateway's USB text output can stay dead after the host lets go (radio and MQTT unaffected); `reboot` on the console brings it back. Scripts must close the port when they stop reading. USBCDC::write waits up to 250 ms per call on a full TX FIFO (64 B); since 2026-11-21 Serial.setTxTimeoutMs(20) bounds it (0 would truncate normal bursts).
- [2026-11-16] [GATEWAY/DELTA_BASE]: An unusable delta (different base id after a gateway restart, or a failed splice) makes the gateway queue a full picture 0xD1 to the camera, at most once per 60 s (image_receiver.cpp requestNewBase). The gateway restarts with the CLI command reboot.

---
- [2026-11-19] [GATEWAY/OTA]: Arduino-ESP32 3.3 `Update.end(true)` accepts an image shorter than announced (it sets the size to the bytes written): check `Update.isFinished()` first. A truncated image with a matching length is still caught in `esp_ota_set_boot_partition()` (image verify, UPDATE_ERROR_ACTIVATE). The S2 libs have CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE: override `extern "C" bool verifyRollbackLater()` to confirm a new app yourself; verified on the bench that a reboot while PENDING_VERIFY boots the previous slot.
- [2026-11-21] [GATEWAY/WEBSERVER]: The core 3.x WebServer blocks loop() before any handler or password check (request line/headers up to 5 s per line and 10 s total, POST body restarted per byte, writes retried 10 x 1 s), which tripped the 5 s loop watchdog: the gateway uses lib/GuardedWebServer (fork of 3.3.12): 3 s per request (408), 2 KB POST cap (413), multipart refused, bounded writes (1360 B pieces, select() writability, drop after 3 s without progress). OTA is still a raw upload (RAW_START/WRITE/END/ABORTED, 1436 B pieces, headers at RAW_START, auth there) exempt from the 3 s request limit but each piece must arrive within 3 s; nothing publishes or prints during an upload. Never include the core <WebServer.h> (lib_ignore).
- [2026-11-21] [GATEWAY/RADIO_TASK]: The CC1101 is read in its own FreeRTOS task (radio_task.cpp, priority 5, 1 ms polling, frames through one 256-entry PSRAM queue in arrival order); it is the only CC1101/SPI owner. Cause (bench 2026-11-20): every HTTP request blocked loop() 10-28 ms and overflowed the 64-byte RX FIFO during picture bursts (two chunks lost every ~2 s while the web page polled /api/status). With the task: 0 overflows and 0 lost chunks in 10-picture load tests, ~0.02 % first-pass loss in a 9 h run. Remaining radio-task stalls of 20-35 ms come from flash writes (NVS, OTA), which suspend all tasks.
- [2026-11-21] [GATEWAY/POLL_DEADLINE]: The camera listens ~104 ms after its poll started (bench polldelay sweep). The gateway skips an answer older than 95 ms before downlinkCommandForPoll (nothing consumed). A synchronous ~35 KB MQTT picture publish before the poll after the last chunk made every picture's ACK poll late (+2 s re-poll); pictures are now published after the poll answer (held while their resend runs).
- [2026-11-21] [GATEWAY/LOOP_WDT]: loopTask is on the 5 s task watchdog (enableLoopWDT() at the end of setup(); wdttest in the eval env verified the reboot, reason task_wdt). Every loop() path must stay under 5 s or feed: MQTT host lookup runs in a helper task (getaddrinfo blocks ~7 s on a silent DNS) with the address cached, broker writes stop after 2 s without progress, an incoming MQTT message over 4 KB per pass drops the connection, CLI scan is asynchronous. OTA over the guarded server verified (no watchdog reset).
- [2026-11-21] [GATEWAY/PER_CAMERA_PICTURES]: image_receiver.cpp keeps all picture state per camera (CamPic slots, IMG_MAX_CAMERAS 4 = DOWNLINK_MAX_CAMERAS, static_assert): reassembly, delta base, large/gray pictures, resend, pending publish and the publish copy buffer per slot. A slot is assigned on the first authenticated chunk and evicted only when idle (no open picture, resend or pending publish); buffers are allocated lazily in PSRAM (2 MB on the S2 Mini), never freed, retried 60 s after a failed allocation. The resend reuses the slot's reassembly buffer (imgDirty wipes it before the camera's next picture). Bench with one camera: e2e 12/12, drop-7 resends complete and published once.
- [2026-11-21] [GATEWAY/DRAM_FULL]: The ESP32-S2's static internal RAM (.dram0.bss) is full: the radio queue, the radio-task stacks/tables, the MQTT DNS task stack and the 4 camera slots (~2.2 KB) all overflowed it and had to move to PSRAM or a one-time heap allocation. Check the link step ("dram0_0_seg overflowed") after adding static buffers.
- [2026-11-21] [GATEWAY/DUAL_CC1101]: SmartRC-CC1101 is replaced by a minimal static SPI driver in `radio_task.cpp` (bounded 200 us MISO-low wait via `gpio_get_level` so SPI pinmux is never detached on core 3.x; 2 ms after SRES). Module #2 shares SCK/MOSI/MISO on `PIN_CS2 = GPIO 2` (ADC1_CH1), `IOCFG1 = 0x2E` on both modules, receive-only (`PATABLE = 0x00`, TX refused) on 869.525 MHz (`FREQ 0x21/0x71/0x7A`) or 868.950 MHz in `pch cal` mode. Bench-verified: both modules online (`testspi 1`/`2` OK, `freqoffset2 = 35` for +55.5 kHz crystal offset), camera e2e 12/12 passed (1457 frames, 0 overflows, 0 poll_late).
- [2026-11-21] [MD_CAM/PICTURE_CHANNEL]: Phase B moves 0x82/0x83 picture chunks to 869.525 MHz (band 54, 10 % duty cycle; CC1110 at 27 MHz: `FREQ 0x20/0x34/0x63`). Gateway advertises `DL_FLAG_PCH` (0x01) + channel 0 in poll answer `[8..9]` (only when `cmd != 0xF0`, `pch on`, module #2 online, not in CAL, not suppressed by the per-camera 2-miss / 15 min..4 h detector). Camera clears `s_pch` after 3 unanswered polls, latches `s_pic_ch` per picture after `0xB2`, switches in IDLE and always returns to 868.950 MHz. Bench-verified: 2,802 PCH chunks / 0 main chunks across D1..D6 + `drop 7` D1 (10 rounds, 1.5 s) and D2 640x480 (27 rounds, 4.0 s), 0 overflows, 0 late polls.
- [2026-11-21] [MD_CAM/PICTURE_TOKEN]: Phase D serializes camera RF bursts via `0xBB` token request (immediate `cmd=0` downlink answer with `DL_FLAG_TOKEN | DL_FLAG_GRANT/HOLD`) and `0xB1` release (`picture_token.{h,cpp}`, pure C++17, ~160 B static RAM, FIFO 4-camera wait queue, `RESERVED` promotion, 10 s/12 s/90 s leases, 3 s ACK grace, legacy camera claim/immediate-release). Camera captures JPEG into SDRAM first, then acquires the token before `0xB2` and releases on `0xBA` ACK or `ack_left` expiry. Bench-verified: e2e 12/12 passed with `grants 6 | holds 0 | releases 6 | expiries 0 | legacy 0`, 1,865 PCH chunks / 0 main chunks, 0 overflows, 0 late polls; gateway web portal shows Radio #2 + Picture Token tiles.
- [2026-11-21] [MD_CAM/DUTY_CYCLE]: Phase E tracks rolling 1 h airtime (7 x 10-min conservative 60–70 min buckets) on both gateway (`duty_cycle.{h,cpp}`, pure C++17, 4 B `.dram0.bss` pointer + one-time `calloc`) and camera (`MD_CAM/firmware/main.c`, 70 B `__xdata`). Counts 24 B packets (7.08 ms / 7 ms) on band 50 (limit 3,600 ms/h) and 56 B chunks (13.74 ms / 14 ms) on band 54 (limit 360,000 ms/h) or band 50 fallback. Policy: fallback to 868.95 MHz is allowed (never blocked/capped) and tracked with dedicated fallback & B50 over-budget counters (`duty` CLI, `/api/status` `duty`, web tiles); camera `#if DUTY_B54_SOFT_LIMIT` only stretches autonomous motion pause (5 s -> 30 s) and defers idle snapshot when B54 > 10 %. Bench-verified across 6 pictures (D1..D6): GW TX 156 ms (4.3 % of B50), camera B50 248 ms (6.8 %) / B54 25,446 ms (7.0 %), 0 fallback, 0 over-budget.
- [2026-11-22] [GATEWAY/SNIFF]: The eval env has the CLI command `sniff [on|off|all|unknown]`. It prints `[Sniff#n]` hex lines for rejected or bad-CRC frames, or for all frames, at most 20 lines/s. The `all` dump runs at the end of handleRadioFrame so it never delays a poll answer. The CC1101 only delivers frames with sync D3 91, 2-FSK at 38.4 kBaud, taken as 58 bytes, so a device using other radio parameters (another sync word, rate or channel) needs an SDR to find them first. Bench-verified in PR #47 on `COM9` with door sensor `2JHL2KMX` (`sniff unknown` silent on auth frames; `sniff all` dumps `[Sniff#n]` after `[AUTHENTICATED]`; `reboot` resets to `off`).
