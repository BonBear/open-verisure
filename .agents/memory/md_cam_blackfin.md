# Memory: MD_CAM Blackfin

## 🧠 Camera Blackfin (ADSP-BF512, U3, JTAG, boot flash)
- [2026-11-16] [MD_CAM/BF_TEST_SOURCES]: Blackfin test sources named below that are no longer in MD_CAM/blackfin (ppi_snap.c, raw_band.c, twi_scan.S, sw_spi_slave.S, rom_spiboot.S, ft232h_jtag.py, u3_reader ...) were removed in de58e96 and live in git history.
- [2026-11-01] [MD_CAM/U5_BLACKFIN]: U5 is an ADSP-BF512 KBCZ-4 (variant WITHOUT internal flash); it boots from its own SPI0 flash (MD_CAM/BF_BOOT_FLASH). Photo: MD_CAM/docs/images/blackfin_bf512_chip.jpeg.
- [2026-11-09] [MD_CAM/BF512_DATASHEET]: ADSP-BF51x Rev. D, 168-ball CSP_BGA: CLKIN=A13, XTAL=A12, CLKBUF=A11, RESET=B10, PG=C13 ("must be pulled low if unused"), EXT_WAKE=B14, VDDOTP=B1, VPPOTP=D3, VDDRTC=B12, VDDFLASH=D12, VDDMEM among others J5/K5/K7. All supplies and CLKIN must be stable 3500 x tCKIN before /RESET is released. Spec: VDDINT 1.10-1.47 V, VDDEXT/VDDMEM 1.7-1.9 / 2.25-2.75 / 3.0-3.6 V, VDDRTC 2.25-3.6 V, VDDOTP/VPPOTP (read) 2.25-2.75 V, CLKIN 12-50 MHz.
- [2026-11-09] [MD_CAM/BF_PINS_POWERED]: Board #1 powered: rails 3.26 / 2.74 / 1.51 (the 1.8 V rail, low) / 1.21 V; X2 = 25.000 MHz crystal between A13/A12 (~1.6 V); EXT_WAKE and VDDMEM (K7) 3.27 V; VDDOTP = VPPOTP = VDDRTC = 2.75 V; PG (C13) = 0.81 V from a divider on the 1.2 V rail, and pulling it to GND changed nothing (not a boot blocker).
- [2026-11-16] [MD_CAM/BF512_L1_32K]: The BF512 has 32 KB of L1 instruction SRAM (0xFFA00000..0xFFA07FFF; 0xFFA08000 reads 0xADADADAD = does not exist). bf512_l1.ld uses 0x8000; L1 data is nearly full (a 600-byte table did not fit).
- [2026-11-01] [MD_CAM/BF_BMODE]: Board #2 U5: BMODE2 (M2) = GND, BMODE0 (M3) and BMODE1 (N1) = 10 kOhm to 3.3 V, i.e. BMODE 011 = SPI0 master boot with /CS on PG15 (G1). Host boot via SPI0 slave (100) or UART0 (111) is impossible without resoldering (tried 2026-11-01, only 0x00 back). HWAIT (M4) unconnected.
- [2026-11-01] [MD_CAM/J5_JTAG]: J5 (8-pin, pin 1 = square pad) is the Blackfin JTAG (confirmed on both boards): 1 = 10 kOhm to 3.3 V (VDDEXT reference), 2 = TRST (N4), 3 = TDI (P2), 4 = TMS (N5), 5 = TCK (P3), 6 = GND, 7 = TDO (N3, 10 kOhm), 8 = EMU (M5). TRST has no pull-down and sits at 0 V when powered: pull it up externally for JTAG.
- [2026-11-08] [MD_CAM/JTAG_IDCODE]: JTAG via J5 and a CJMCU FT232H (AD0=TCK, AD1=TDI, AD2=TDO, AD3=TMS, 1 MHz): one device, IDCODE 0x227E80CB (BF51x, ADI). Blackfin IR is 5 bits (IDCODE 00010, DBGCTL 00100, DBGSTAT 01100, EMUIR 01000, EMUDAT 10100, EMUPC 11110). urJTAG's "dr" prints MSB first.
- [2026-11-10] [MD_CAM/BF_JTAG_LOAD_OK]: bfin-gdbproxy in WSL (root, background) + Windows bfin-elf-gdb against localhost:2000 halts the core and loads/runs our own ELFs. DBGSTAT IN_RESET (0x1000) means /RESET B10 is low (P1_0/Q7, see MD_CAM/Q7_RESET): check B10 before JTAG troubleshooting.
- [2026-11-11] [MD_CAM/CC_BF_SPI]: The CC1110 reaches the Blackfin's SPI1 on port H only while P1_2 = 1 (P1_2 enables a bus switch/buffer and pulls PH0 SPI1_SSEL low; with P1_2 = 0 PH0..PH3 read 1): P1_4 -> PH1 SPI1_SCK, P1_5 -> PH3 SPI1_MOSI, PH2 SPI1_MISO -> P1_3. P1_1 does not affect PH; P0_4/P0_5 (UART) and the other CC pins reach no PF/PG/PH pin. The earlier "P1_2 is /SPISS, P1_1 a bus switch, CC must tri-state for the boot" entries (2026-10-28/30) were wrong.
- [2026-11-11] [MD_CAM/BF_SW_SPI_OK]: The Blackfin's hardware SPI1 slave never received anything (PORTH_FER 0x000F, all PORTH_MUX values, SPI1_CTL 0x4029/0x4028/0x4428 tried); a software SPI slave (mode 0, MSB first, bit-banged CC master ~300 kHz) works both ways and is what snap_link uses. If RF packets stop, check the Blackfin via JTAG before assuming the CC hung.
- [2026-11-11] [MD_CAM/BF_TWI_SCAN]: The Blackfin's TWI bus has two devices: 0x40 = the camera sensor (16-bit register addresses, ignores 8-bit pointers) and 0x5C = a BH1750-like light sensor (command-driven: never write "register pointers" to unknown TWI devices). MMR access must be 16/32-bit; a byte write to TWI_XMT_DATA8 caused an exception. The camera module is a Sunny "8811GA" on a 24-pin FPC (J1, usual OmniVision layout); U4 is an ISSI IS42S16800F 16 MB SDRAM on the EBIU.
- [2026-11-12] [MD_CAM/CAMERA_OV7955]: Sensor chip ID 0x300A/0x300B = 0x79/0x55, probably an OmniVision OV7955 (VGA, 60 fps, parallel DV); it runs as soon as the Blackfin is released (XCLK/PCLK clocking, VSYNC period 16.4 ms).
- [2026-11-12] [MD_CAM/OV7955_TIMING]: With the factory clocking the sensor runs 640x480 at ~25 MHz PCLK: HREF period 780 PCLK with 640 active, VSYNC period 525 lines (high 128 PCLK). Measured with timer 0/1 in WDTH_CAP with CLK_SEL counting PPI_CLK.
- [2026-11-12] [MD_CAM/BF_PPI_PINS]: Camera parallel bus: PCLK = PG5 (PPI_CLK), HREF = PG6 (PPI_FS1), VSYNC = PG7 (PPI_FS2), D2..D9 = PF2..PF9 (PF0/PF1 static). PG5 looks static under GPIO sampling because PCLK is synchronous with the Blackfin clock.
- [2026-11-16] [MD_CAM/FLASH_PINS]: The IR flash board (J2/J3, powered via aux P0_7; red LED on when powered) is driven by Blackfin PF10 and PF12, active high (PF10 has a ~1 ms start delay). PF11 is pulsed low by the original, PF13 is the chip select of an SPI1 device (SPI1 shares pins with the CC1110 link, do not touch), PH4 is an on/off output. The diodes are invisible IR.
- [2026-10-30] [MD_CAM/U3_CS_IS_P1_1]: U3 (marked "DSP V175") is an EON EN25F40 4 Mbit flash, JEDEC 1C 31 13. Its /CS follows CC1110 P1_1 inverted (P1_1=1 selects); it is the CC1110's own flash, not the Blackfin's boot flash. The 2026-10-28/30 entries calling P1_1 a bus switch or /CS the Blackfin's SPI0_SEL1 were wrong.
- [2026-10-30] [MD_CAM/U3_DUMP_METHOD]: U3 reads reliably from the CC1110 with the Blackfin in reset, USART0 SPI mode 0 (353 kHz) and P1_1 as /CS around each command (the dump routine was removed in the cleanup, see git history).
- [2026-10-31] [MD_CAM/U3_CONTENT]: U3 holds no Blackfin image on either board: only 0x07E000 (135 B 0x00), 0x07E200 (1 B on Board #1, 3 B on Board #2) and 0x07F000 (3 B) are written; it is configuration memory. Board #2's original CC1110 firmware reads these pages at power-on (2 MHz: RDSR, RDID, Fast Read 0x07F000/0x07E200/0x07E000/0x000000/0x020000/0x040000).
- [2026-10-31] [MD_CAM/BOARD2_WAKE_CYCLE]: Reference Board #2 (original firmware, unpaired) never starts the Blackfin at power-on, on PIR or on SW3 (Saleae 60 s): it reads U3 and writes ":OK; \n" on UART TX (P0_4, 115200 8N1) every ~0.8 s / ~2.5 s, with RESET_N and VBAT stable. P1_2 stays low.
- [2026-10-30] [MD_CAM/BLACKFIN_NO_BOOT]: Superseded: the October "Blackfin does not boot / never clocks U3 / SPI lines pulled low" measurements on Board #1 are explained by P1_0 holding /RESET via Q7 and by the Blackfin booting from its own EN25F20 on SPI0, not U3.
- [2026-11-14] [MD_CAM/BF_BOOT_FLASH]: The Blackfin's boot flash on Board #1 is an EON EN25F20 (JEDEC 1C 31 12, 256 KB) on SPI0 (PG12 SCK, PG13 MISO, PG14 MOSI, PG15 CS). The factory boot stream was 0x7FD4 bytes in 23 blocks (init block 0x110 bytes, all header checksums OK); dumps with SHA-256 list are in C:\repo\verisure_firmware_dumps (bootflash_0000_8000.bin also in the user's Documents).
- [2026-11-16] [MD_CAM/NO_FACTORY_CC]: md_cam_orig.bin (the camera's 2026-10-24 "factory CC1110 dump") is all 0xFF: Board #1's factory CC1110 firmware was never captured, and the door sensor's original was never dumped. Check a dump for content, not just its hash. The only factory CC1110 left is on the locked Board #2.
- [2026-11-14] [MD_CAM/BF_ROM_SPIBOOT]: ROM bfrom_SpiBoot (0xEF00000A; R0 = flash address, R1 = flags, R2 = 0, [SP+12] = hook) starts a boot stream from any flash address. Flags for the flash on PG15: 0x03A00000 (PERIPHERAL | NOAUTO | ALTERNATE | TYPE_3); without ALTERNATE PH8 is used and the header reads 0xFF. The ROM does no pin muxing: set PORTG_FER 0x7C60, MUX 0x0480, PG15 output high and PORTH_FER bit 8 first.
- [2026-11-16] [MD_CAM/BF_FLASH_LAYOUT]: Boot flash layout: 0x0000 boot_select.ldr (272 bytes; reads PH0 16 times, low = boot 0x8000, which the CC1110 always arranges), 0x8000..0xFFFF snap_link.ldr (~15-17 KB), 0x10000.. the factory copy, erased 2026-11-16. Selector pitfalls: the ROM DMAs headers to 0xFF807FF0, so with DMEM_CONTROL 0x101B (cache) DMA7 errors (the selector sets 0x1001 and clears DMA7); a failed ROM call leaves SPI0/DMA7 state that offsets the next read. Restore sector 0 from build/fw_dump/orig_sector0.bin with flash_sector0.c (4 KB erase only, confirmation word 0x5EC70000).
- [2026-11-16] [MD_CAM/BF_FLASH_16K]: flash_write.c (only addresses >= 0x8000, blank check before, compare after) takes at most 0x4000 bytes per run (buffer in L1 bank B 0xFF900000) and answers result 1 for more: write in 16 KB parts with gdb `restore FILE binary BIAS START END`, check result 0 per part (bf_flash.sh). Erasing our area: 0xFF80001C = 0xE7A5E000. The boot ROM reads the LDR without a size limit.
- [2026-11-12] [MD_CAM/BF_DMA_ORDER]: MDMA only works when the SOURCE stream is enabled before the DESTINATION (HRM Listing 6-2); in the reverse order the destination stays at DMA_RUN forever and CURR_ADDR is never loaded (only loaded on the first memory access). DMA_DONE needs DI_EN. This, plus the missing SDRAM init (MD_CAM/SDRAM_HIRES), explained the earlier "DMA never starts / SDRAM read hangs".
- [2026-11-14] [MD_CAM/CONT_CAPTURE_OK]: Pitfall after the boot path: IVG15 is pending with IMASK 0x801F and EVT3/EVT15 point to old L1 content, so an exception gives a double fault that locks the core (only a power cycle helps). snap_link does CLI and sets EVT3 to its own handler that logs SEQSTAT/RETX at 0xFF800020/24.
- [2026-11-15] [MD_CAM/BF_CTRL_WORDS]: After flash boot, snap_link's L1 control words hold leftover memory even after a short power cycle (seen 0x1000 as delta threshold); main() zeroes the sensor-register, delta-threshold and AWB words. The JTAG start-test words 0xFF80002C/0xFF800048 are not zeroed.
- [2026-11-16] [MD_CAM/BF_O2]: snap_link is built with -O2 and -nostdlib (no missing libgcc symbols): capture+encode 320 0.86 -> 0.29 s, 640 2.61 -> 0.60 s, LDR 17.7 -> 15.4 KB. bf512_l1.ld places .rodata/.data/.bss in L1 data from 0xFF800100, 4-byte aligned (an uneven .bss start broke LDR block headers); gdb load does not zero .bss.
