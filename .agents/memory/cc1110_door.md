# Memory: CC1110 General & Door Sensor

## ⚙️ CC1110 General (clocks, PM2, sleep timer, flash, AES, SDCC)
- [2026-10-22] [CC1110/RF]: The RF core runs at 868.950 MHz with a 27 MHz crystal (X1). Register calculations for frequency and baud rate must be based on 27 MHz, not the standard TI 24 MHz or 26 MHz.
- [2026-10-22] [CC1110/DMA]: The RFD FIFO must be handled via DMA trigger 19 (DMA_TRIG_RADIO) to guarantee that no bytes are dropped at high transmission rates.
- [2026-10-24] [CC1110/PM2]: The Port 1 edge is selected with PICTL bit 1 (P1ICON = 0x02), NOT 0x04; the wrong bit made the PIR wake only on the wrong edge. PM2 requires the CPU to be switched to the HS RCOSC first (CLKCON.OSC=1) before PCON.IDLE is set; every ISR must clear SLEEP.MODE and PxIFG before PxIF.
- [2026-11-18] [CC1110/SLEEP_CLOCK]: The CC1110 calibrates its 32 kHz RC oscillator to f_xosc / 750 = 36.0 kHz with the 27 MHz crystal, not 32 kHz. The old WOR_RES 2 x EVENT0 16 gave 0.455 s ticks (polls 27.3 s apart); both firmwares now use WOR_RES 1 x EVENT0 563 = 0.5004 s (cc1110_common/sleep_timer.c), camera polls verified 30.0 s apart.
- [2026-11-19] [CC1110/PM2_ALIGN]: The CC253x rule that the instruction after the PCON.IDLE write must not start on a 4-byte boundary has no measurable effect on the CC1110 (door firmware at 0x0438 vs 0x0439, same Otii recording, 1.56 vs 1.55 uA). No build check needed.
- [2026-11-17] [MD_CAM/ADC_AFTER_PM2]: The VDD/3 ADC reads ~110 mV low for several ms after waking from PM2 (2861 mV ~3 ms after wake vs 2969-2976 mV later); a second back-to-back conversion does not fix it. Wait ~11 ms (delay_ms(4)) before an idle battery reading (read_battery_idle_mv, used by camera and door sensor).
- [2026-11-16] [MD_CAM/CC1110_AES_WAIT]: ENCCS.RDY does not come up after encrypt/decrypt until ENCDO has been read, so a long RDY poll (timeout 50000) cost 44 ms per AES block; key loading is not affected. aes_wait() (cc1110_common/aes.c) waits at most ~0.1 ms: a 24-byte packet now takes ~8 ms instead of 52 ms.
- [2026-11-17] [CC1110/FLASH_WRITE]: Writing flash from code running in flash works with DMA (trigger 18 FLASH, destination FWDATA at XDATA 0xDFAF, FCTL.WRITE after arming) and FWT 0x23 at 27 MHz; page erase (FADDRH = page << 1, FCTL.ERASE, wait BUSY) also runs from flash. Verified with the counter log (11 boots, two erases per page).
- [2026-10-22] [SDCC/8051]: The CC1110 is compiled with SDCC. Avoid dynamic allocation (`malloc`) entirely because of the 8051's limited XDATA/IDATA RAM.
- [2026-10-29] [SDCC/MEMORY_MODELS]: With --model-large, `__code` pointers (ROM) must not be passed to transmit functions that use `MOVX` without first copying into an `__xdata` buffer. Reading beyond XDATA into the SFR address space (0xF000+) hangs the 8051 bus.
- [2026-10-29] [CC1110/UART_ISR]: In a USART RX ISR, `U1DBUF` must be assigned to a `volatile uint8_t`; `(void)U1DBUF;` is optimized away by SDCC, the RX flag is never cleared and the interrupt storms.
- [2026-11-19] [BUILD/SDCC_LOOP_REVERSE]: SDCC 4.5/4.6 warn 158 ("overflow in implicit constant conversion") on `for (uint8_t d = 0; d < N; d++)` with N >= 128: loop reversal makes a djnz count-down whose trip count overflows a signed char. Write such delays as a count-down (`for (d = N; d != 0; d--)`): same code, no warning.
- [2026-11-19] [BUILD/SDCC_W110]: Warning 110 ("conditional flow changed by optimizer") means a run-time `if` on a value SDCC proved constant (e.g. `cmd = BF_IMG_CMD; if (cmd == 0xD3)`); make such config-dependent choices with `#if` instead.

---
- [2026-11-19] [CC1110/COUNTER_LOG]: Flash faults (cut write/erase, worn cells) only leave bits at 1, so a log entry check must be unidirectional-error-proof: an XOR check byte let a cut second word read as block 0xFEFFFF; the 0-bit count (Berger code) never passes. Also: never send a block above newest logged + 1, never log or switch pages without the crystal, never erase the other page before the current one holds the newest entry.

## 🚪 Door Sensor (VerisureDoorSensor)
- [2026-10-22] [SENSOR/GPIO]: The reed switch is on P1_7, Shock/Vibration on P1_2, and Tamper on P0_1 (reed and tamper close to GND).
- [2026-11-17] [DOOR/J2_PINS]: On J2, pad 4 is DD (P2_1) and pad 5 is DC (P2_2), the reverse of the old docs (fixed). ESP32 DevKit flasher: GPIO 23 (DD) -> J2-4, GPIO 19 (DC) -> J2-5, GPIO 33 (RST) -> J2-6, GND -> J2-7. '#INIT 0000'/'FFFF' meant swapped lines; the flasher's PINS command shows the running firmware toggling P2_1 at every packet.
- [2026-11-17] [DOOR/TX_EDGE]: The sensor's own transmission puts a falling edge on the shock input P1_2 (seen in P1IFG right after radio_send), so each packet reported a shock and triggered the next (a packet every 0.31 s forever). Fix: after radio_send, with EA=0, clear P1IFG bit 2 and the saved flag and resync the shock level.
- [2026-11-17] [DOOR/BATTERY_GUARD]: Below 2.3 V at boot the sensor neither logs a counter entry nor sends; it sleeps and re-measures every BOOT_RECHECK_S 60 s (was ~55 s before the sleep-clock fix). Tested on the Otii: nothing at 2.1 V, boot packet ~35 s after raising to 3.0 V.
- [2026-11-17] [DOOR/EVENTS]: PM2 firmware verified: reed, shock and tamper each send at once (~0.33 s between packets when toggled fast); a loose magnet bounces the reed on knocks. Gateway frequency error for the door sensor after FSCTRL0: +3.2 kHz.
- [2026-11-19] [DOOR/IDLE_TICK]: Idle 26.3 uA at 3.0 V (Otii 2.6 h, lid on): the PM2 floor is a few uA and each 0.5 s tick costs ~12 uC (clock_xosc() waits ~4 ms at 5.4 mA). The 2026-11-17 value of 17.9 uA was an Otii floor offset artefact (-6 uA), but its findings hold: dropping the pull-ups of closed switches in PM2 works (same current with reed/tamper closed or open), and handling the sensor during a recording gives ~40 mA TX peaks, so measure only when left alone.
- [2026-11-19] [DOOR/RCOSC_TICK]: The door sensor runs its 0.5 s tick on the HS RCOSC and starts the crystal only before a packet (on main since PR #7): tick wake-ups 2.2 uC (2 ms, 2.1 mA peak), ~4.7 uA average vs ~21 uA with the crystal; heartbeats 3602-3606 s apart over 9 h (+0.1 %); reed, shock and tamper verified in both directions. The tamper switch sits near its threshold: a lid lifted gently may not register (mechanical, not firmware).
