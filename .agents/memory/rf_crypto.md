# Memory: RF Link, Crypto, Replay & Protocol

## 📡 RF Link (CC1110 / CC1101, 868.950 MHz)
- [2026-10-24] [MD_CAM/RF]: The camera (Board #1 = 2NCEKS3T unlocked, Board #2 = 2NCEKT3X locked reference) uses a 27.000 MHz crystal (Y1) and the same radio setup as the door sensor: FREQ=0x202EEF, MDMCFG4=0x8A, MDMCFG3=0x75, FSCAL0=0x1F (must stay 0x1F). The old "set is_por_reset on external reset too" trick for the replay filter is replaced by the persistent counter (GATEWAY/REPLAY_COUNTER); is_por is now set only on a power-on reset.
- [2026-11-19] [CC1110/DATA_RATE]: MDMCFG4/3 = 0x8A/0x75 at 27 MHz give 38,418 Bd on the door sensor and camera; the gateway's CC1101 (26 MHz) uses 0x8A/0x83 = 38,383 Bd. The 0.09 % difference is harmless; quote 38,418 for the devices.
- [2026-11-16] [GATEWAY/RX_FIFO_FLUSH]: Running enterRxMode() (SIDLE + SFRX + SRX) after every packet with MCSM1 RXOFF_MODE = RX flushed the next packet already arriving (a third lost at one packet per ~9 ms). Restart RX only if MARCSTATE is not RX (0x0D).
- [2026-11-16] [MD_CAM/RF_PACKET_SIZE]: Camera picture packets are 56 bytes (type 0x82/0x83: 8-byte ID + 3 AES blocks CBC with zero IV, 40 bytes of JPEG; transmit_big_chunk sets PKTLEN 56 and back to 24). The gateway receives a fixed 58 bytes with hardware CRC off and checks CRC-16 (0x8005, init 0xFFFF) in software after 56 bytes, otherwise after 24 bytes; the FIFO is read in pieces and the last byte is left until the frame is complete (errata). Downlinks use PKTLEN 24 with CRC on. Drawback: after a 24-byte packet the gateway listens to noise for ~7 ms.
- [2026-11-17] [GATEWAY/FREQ_OFFSET]: The gateway's first CC1101 module received ~+60 kHz off channel (crystal ~69 ppm low; FREQEST pinned at the FOC limit); strong bench signals hid it, at -83 dBm almost every packet failed CRC. Fix: FSCTRL0 offset (1.587 kHz/step, RX and TX), NVS setting `freqoffset` (default 0; this gateway uses 38 via DEFAULT_FREQ_OFFSET). Read FREQEST when the first frame bytes arrive. FOC_LIMIT BW/2 (FOCCFG 0x17) let the loop wander on noise; FOCCFG stays 0x16.
- [2026-11-17] [GATEWAY/ANTENNA]: The CC1101 module's helical spring antenna cost ~27 dB; a straight 22 AWG wire (~8.0 cm) raised the camera from -85 to -57 dBm and cured lost polls and 34-59 % chunk loss that looked like Blackfin regulator noise. Check the antenna before blaming firmware for range problems.

---
- [2026-11-20] [RF/GATEWAY_TOO_CLOSE]: A gateway antenna right next to the camera (gateway fell over on the bench) overloads the CC1101: camera packets at -17/-18 dBm arrive with a 20-50 kHz frequency error that changes per packet and fail the CRC, while far devices still pass. The camera then keeps its Blackfin on resending (~175 mA for 6-8 min) and idles higher (~0.13 mA). Keep the gateway >= 0.5 m away (60 cm: -38 dBm, -1.6 kHz, all accepted). A strong invalid-CRC packet with a wandering frequency error means receiver overload, not a device fault.

## 🔐 Crypto, Replay & Protocol
- [2026-10-22] [AES/KDF]: The CC1110 uses its hardware AES-128 coprocessor. Device key = AES-128-ECB(master key, 8-character device ID from the casing, zero-padded to 16 bytes) (derive_key.py).
- [2026-10-22] [PAYLOAD]: A regular packet is 24 bytes: 8-byte ID header + one 16-byte AES block (flags, battery level VDD/3, contact state, counter).
- [2026-10-22] [REPLAY]: Superseded: the 16-bit rolling seq (restarting at 0 on reset, let through by the power-on flag) is only the legacy format; door sensor and camera now send the persistent 32-bit counter (GATEWAY/REPLAY_COUNTER), and a device that has sent it is never accepted in the old format again.
- [2026-11-17] [GATEWAY/REPLAY_COUNTER]: Door and camera packets carry a 32-bit counter (flag 0x20, low half in plain[0..1], high half in plain[14..15], reset cause in flags[7:6]); the device logs the upper 24 bits in flash pages 30-31, the gateway keeps the last counter in NVS namespace 'replay' and accepts only strictly increasing values (no reset/tamper exception). A device reflashed without a seed: run 'replay reset <ID>' on the gateway, then power-cycle it (only a boot packet is accepted after the reset).
- [2026-11-17] [DOOR/COUNTER_SEED]: Reflashing erases the device's counter log; build_and_flash.py (and build_and_flash_md_cam.py) reads the gateway's last counter (GET http://<gateway>/api/replay?id=<ID>, env GATEWAY_HTTP) and builds with -DCTR_SEED so the counter continues without 'replay reset'.
- [2026-11-17] [MD_CAM/PERSISTENT_COUNTER]: The camera uses the door sensor's counter log (pages 30-31, --code-size 0x7800, CTR_SEED, battery guard below 2.3 V). 24-byte packets: [12] type (0xBA poll, 0xB9 motion, 0xB8/0xB3 picture failed, 0xB2 picture start, 0xB5 tamper, 0 announce), [13] argument, [14..15] counter high half. The poll answer echoes the 32-bit counter in [2..5]; the gateway answers only counter-format polls. A ~10 s power cut does not reset the camera (~3 uA idle, capacitors hold it): cut 90 s to test a real power-on reset.
- [2026-11-17] [MD_CAM/CHUNK_TAG]: Picture chunks (0x82/0x83) carry the counter of the picture's start packet (0xB2): low 16 bits in plain[0..1], high 16 bits in plain[46..47]. The gateway rebuilds the tag from lastCtr and accepts -128..+64 with matching high half; 0x82 only for the newest tag or newer, 0x83 only for exactly the newest (per-device picTag, RAM only). Legacy 0x80 chunks are not accepted. Bench-tested with -DPIC_TAG_SKEW.
- [2026-11-15] [GATEWAY/KCV]: The gateway never prints the master key; boot and the CLI command status show a check value = first 3 bytes of AES(key, 0^16), to compare with the same calculation on secrets.h. The alarm switch follows CLI and MQTT (verisure/alarm/set ON/OFF, anything else ignored); state is published retained on verisure/alarm/state.
